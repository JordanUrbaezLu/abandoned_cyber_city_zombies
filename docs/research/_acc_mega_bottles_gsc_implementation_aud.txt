## 2. Does GSC-only clientfield::register("toplayer", ...) crash without a matching .csc registration?

Signatures (stock): GSC `function register(str_pool_name, str_name, n_version, n_bits, str_type)` → `RegisterClientField(...)` (clientfield_shared.gsc:17-20). CSC `function register(str_pool_name, str_name, n_version, n_bits, str_type, func_callback, b_host, b_callback_for_zero_when_new)` → `RegisterClientField(...)` (clientfield_shared.csc:20-23). `VERSION_SHIP = 1` (version.gsh:36) — our literal `1` matches. `CF_HOST_ONLY = true`, `CF_CALLBACK_ZERO_ON_NEW_ENT = true` (version.gsh:102-103); stock idiomatically passes `!CF_HOST_ONLY` to mean false.

Stock pairing evidence (deadshot, exactly as asked):
- _zm_perk_deadshot.gsc:71-72 (`deadshot_register_clientfield`): `clientfield::register("toplayer", "deadshot_perk", VERSION_SHIP, 1, "int")` AND `clientfield::register("clientuimodel", PERK_CLIENTFIELD_DEAD_SHOT, VERSION_SHIP, 2, "int")` (PERK_CLIENTFIELD_DEAD_SHOT = "hudItems.perks.dead_shot", _zm_perks.gsh:9).
- _zm_perk_deadshot.csc:47-48 (`deadshot_client_field_func`): registers the SAME pool/name/version/bits/type, adding client-only args `&player_deadshot_perk_handler, !CF_HOST_ONLY, CF_CALLBACK_ZERO_ON_NEW_ENT` (and `undefined` callback for the clientuimodel one).
- _zm_perks.gsc:1628 vs _zm_perks.csc:38: "scriptmover"/"clientfield_perk_intro_fx" 1-bit field registered on BOTH sides, gated by the SAME `level.zombiemode_using_perk_intro_fx` condition on both sides — i.e. even CONDITIONAL registration must match.

Corpus-wide diff (I extracted every `clientfield::register(pool, name` from stock zm/+shared/ .gsc vs .csc, normalized whitespace): after resolving false positives (("toplayer","perk_vulture") appears only inside a doc comment at _zm_perks.gsc:1946; ("toplayer","sndPlayerConsumed") IS registered client-side via a multi-line call at archetype_thrasher.csc:69-76; macro-vs-literal pairs like COUNTER_UAV_NAME="counteruav"), there are ZERO genuine GSC-only registrations in the "toplayer"/"allplayers"/"actor"/"scriptmover"/"world" pools. Stock discipline is 100% both-VM registration for those pools.

THE ONE EXCEPTION — pool "clientuimodel" does NOT require a .csc registration: zm_usermap.gsc:100-103 (`function autoexec init_fx()`) registers `clientfield::register("clientuimodel", "player_lives", VERSION_SHIP, 2, "int")` and zm_usermap.csc contains NO registration at all (only `#using scripts\shared\clientfield_shared` at line 4). Every working usermap executes this code, so GSC-only clientuimodel registration provably does not crash. The reason is documented in stock itself: _weaponobjects.gsc:70 — `clientfield::register("clientuimodel", "hudItems.proximityAlarm", ...); // registered client-side in raw/ui/uieditor/clientfieldmodels.lua` — i.e. the client half of clientuimodel fields lives in LUI lua, not .csc.

CONCLUSION for our code: `_acc_mega_bottles.gsc:34-40` ("toplayer","acc_mega_bottles",4 bits) and the sister module `_acc_data_shards.gsc:51` ("toplayer","acc_data_shards") are GSC-only "toplayer" registrations with no .csc counterpart. The repo's own recorded knowledge says mismatched registration fails at load (zm_abandoned_cyber_city.csc:30-31: "must match the entry .gsc #using or clientfield registration mismatches at load"). Engine internals can't be proven from scripts alone, but: (a) toplayer fields are bit-packed playerstate data the client must decode by registration order/width, (b) stock has zero counterexamples, (c) community-documented failure is a fatal clientfield-mismatch error at map load. Treat GSC-only "toplayer" registration as a crash. Three remediations, safest first:
1. Switch pool to "clientuimodel" (e.g. name "hudItems.accMegaBottles") — proven safe GSC-only per zm_usermap.gsc:102 — BUT you MUST also switch the setter: clientuimodel fields are set with `clientfield::set_player_uimodel` (→ CodeSetUIModelClientField, clientfield_shared.gsc:71-77), not `set_to_player` (→ CodeSetPlayerStateClientField, clientfield_shared.gsc:55-58). Stock pattern: register _zm_score.gsc:36, set _zm_powerup_double_points.gsc:86.
2. Keep "toplayer" and add a matching register to the entry .csc (zm_abandoned_cyber_city.csc main(), or a future _acc .csc module): same pool/name/version/bits/type, callback can be `undefined` (stock precedent: _zm_perk_deadshot.csc:48 passes undefined), flags `!CF_HOST_ONLY, CF_CALLBACK_ZERO_ON_NEW_ENT`.
3. Delete the registration + sync calls entirely until Phase 4 (iprintln already provides feedback).

Registration timing note: our register runs inside `level thread acc_main::init()` (entry gsc:167 → _acc_main.gsc:78). A GSC thread executes synchronously until its first wait, and none of the init() bodies that run before acc_mega_bottles::init contain a live wait/waittill (verified by scan; only comments mention waittill), so the call lands inside main()'s load frame. Stock, however, registers earlier — via `autoexec` (zm_usermap.gsc:100) or REGISTER_SYSTEM `__init__`. Usermap main()-time registration is the standard community pattern, but mark it TODO(acc-verify) for the first Windows compile.

## 3. _zm_stats.gsc relevance

_zm_stats.gsc contains ZERO clientfield usage (grep across the whole file: no matches). It is the persistence module: `player_stats_init` seeds `globallogic_score::initPersStat` counters ("kills","downs","perks_drank","bgbs_chewed",... lines 31-80); wrappers `get/set/add/increment_global_stat` (307-342), `add_client_stat/increment_player_stat/set_client_stat` (353-411), map stats (424-467); exposes `level.add_client_stat` / `level.increment_client_stat` function pointers (_zm_stats.gsc:26-28). It is NOT a HUD path — only relevant to mega bottles if you ever want cross-match persistent stats (e.g. `[[level.add_client_stat]]("acc_bottles_earned", n)` style), not for in-run display.

## 4. Safest greybox HUD path without LUI

- iprintln (already implemented at _acc_mega_bottles.gsc:87-88, 129, 149, 155): zero client-side requirements, but transient feed text only — fine for events, not a persistent counter.
- BEST GREYBOX OPTION — classic GSC hudelems, which are fully alive in BO3 ZM stock code, server-side .gsc only, no .csc, no lua, no clientfield: `NewClientHudElem(player)` is used by stock ZM at _zm.gsc:4880-4899 (downed-state text: sets .alignX/.alignY="center"/"middle", .horzAlign/.vertAlign="user_center"/"user_bottom", .foreground=true, .font="default", .fontScale=1.8, .alpha, .color, SetText, FadeOverTime), _zm_laststand.gsc:634/748/1199, _zm_craftables.gsc:2642, _zm_equipment.gsc:547. The helper layer is `scripts\shared\hud_util_shared`: `hud::createFontString(font, fontScale)` (hud_util_shared.gsc:334-350; call ON the player: `elem = player hud::createFontString("default", 1.5)` — it does `newClientHudElem(self)` and `setParent(level.uiParent)`), positioned with `hud::setPoint(point, relativePoint, xOffset, yOffset)` (hud_util_shared.gsc:53). For the number itself use `elem SetValue(count)` — numeric, needs NO localized string (stock ZM usage: _globallogic.gsc:758, _hud_message.gsc:225/269). Stock always passes localized `&"REFS"` to SetText (_zm.gsc:4890); raw-string SetText is common in usermaps but unverified here, so for pure greybox prefer SetValue-only (or SetValue plus an iprintln legend).
- Concretely: drop (or comment out) the clientfield register/set in _acc_mega_bottles.gsc and have `sync_bottle_count_to_client` create-once + `SetValue` a per-player font string. This removes the .csc-mismatch risk AND gives a persistent on-screen counter with zero new files. The clientfield bridge returns in Phase 4 when real LUI widgets exist (docs/16_gsc_reference.md:444-450 describes that pipeline; docs/14_controls_and_hud.md:98 expects the `acc_mega_bottles` clientfield name).

GOTCHAS:
- GSC-only 'toplayer' clientfield registration (_acc_mega_bottles.gsc:34-40 AND _acc_data_shards.gsc:51) has no .csc counterpart: stock registers every toplayer/allplayers/actor/scriptmover/world field in BOTH VMs with identical pool/name/version/bits/type (deadshot gsc:71-72 vs csc:47-48), and the repo's own .csc comment (zm_abandoned_cyber_city.csc:30-31) records 'clientfield registration mismatches at load' as the failure mode — treat as a map-load crash until proven otherwise on the Windows box.
- The ONLY pool safe to register GSC-only is 'clientuimodel' (proof: zm_usermap.gsc:102 registers 'player_lives' with no csc counterpart and every usermap runs it; client half lives in raw/ui/uieditor/clientfieldmodels.lua per _weaponobjects.gsc:70 comment) — but if you switch pools you MUST also switch the setter from clientfield::set_to_player to clientfield::set_player_uimodel; set_to_player on a clientuimodel field calls the wrong engine path (CodeSetPlayerStateClientField vs CodeSetUIModelClientField, clientfield_shared.gsc:55-58 vs 71-77).
- 4-bit clientfield (0-15) but grant_bottle has NO cap (_acc_mega_bottles.gsc:20 vs 84): server-side count can exceed 15 (4 players x many boss kills), and set_to_player with a value over the registered bit width silently corrupts/wraps the transmitted value — clamp to 15 or widen the field.
- try_apply_mega (_acc_mega_bottles.gsc:145) has ZERO callers repo-wide — the perk-machine 'use' handler described in the comment block (134-143) doesn't exist, so the whole bottle-consumption/Mega path is dead code; only boss-drop acquisition is wired (_acc_boss.gsc:98,133).
- Specialty-key mismatch lying in wait: mega_display_name uses invented keys 'specialty_acc_deadshot'/'specialty_acc_widows_wine'/'specialty_acc_aura_blast' (_acc_mega_bottles.gsc:195-197) while live has_mega_perk consumers query STOCK keys 'specialty_deadshot' (_acc_damage.gsc:97), 'specialty_widowswine' (_acc_damage.gsc:77), 'specialty_electriccherry' (_acc_perk_aura_blast.gsc:102; defines at _zm_perks.gsh:29/31/35). Whichever key set the future set_mega_perk caller uses, one side silently fails: flags never match (queries return false forever) or display falls through to 'Mega Perk'. Unify on the stock specialty strings.
- CSC clientfield::register takes 8 args (callback, b_host, b_callback_for_zero_when_new — clientfield_shared.csc:20); when adding the client half, callback may be 'undefined' (stock precedent _zm_perk_deadshot.csc:48) but pool/name/version/bits/type must match the GSC call EXACTLY, including conditional gating (stock gates both sides on the same level flag, _zm_perks.gsc:1626-1629 vs _zm_perks.csc:35-39).
- Registration timing: clientfield::register currently executes inside 'level thread acc_main::init()' (entry gsc:167) — safe today only because no _acc_ init() that runs before acc_mega_bottles::init (_acc_main.gsc:69-78) contains a wait; if any earlier init ever gains a wait()/waittill, the register slips past the load-frame snapshot window (stock registers via autoexec/__init__ pre-main, zm_usermap.gsc:100).
- For greybox HUD, avoid SetText with raw strings (stock only ever passes localized &"REFS", _zm.gsc:4890); use elem SetValue(n) for the counter (stock numeric precedent _globallogic.gsc:758, _hud_message.gsc:225) — no localization, no precache, no .csc.
- _zm_stats.gsc is a red herring for HUD work: it contains zero clientfield calls; it is the persistent cross-match stat system (initPersStat/add_client_stat) only.
